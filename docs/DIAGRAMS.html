01

Architecture: one request, top to bottom

Three layers with one job each. HTTP concerns stay in PL, every business rule lives in BLL, and DAL is the only code that talks to the database.

How to explain it

  • "Three layers, one job each: PL is HTTP, BLL is every business rule, DAL is the database. Controllers are thin and only call a service."
  • "Authentication does more than check the token. It also checks the user still exists, isn't blocked and still has that role, so blocking someone takes effect immediately."
  • "Every error has the same shape, so the frontend only needs one error handler."
  • "The database is the last safety net. Even if a bug skipped a check in code, the indexes and constraints would still stop bad data."
02

Who sees what

One visibility rule decides which projects a user can see. Every list, approval, report and PDF goes through it.

How to explain it

  • "There's exactly one visibility rule, ProjectAccessService, and every service uses it, so it can't drift between endpoints."
  • "Out of scope is 404, not 403, on purpose: you can't even find out that someone else's project exists."
  • "403 is only for the wrong role, and that's checked before the request reaches the controller."
03

Data model

Six tables. The rules that must never break are enforced by the database itself, not only by code.

How to explain it

  • "Actual hours are never stored. They're always the sum of approved entries, so they can't drift out of sync."
  • "One entry per employee, project and day is a filtered unique index: cancelled entries don't count, so cancelling frees the day."
  • "Nothing important is hard-deleted. Clients are deactivated, team members are marked removed, and reviews are kept as history."
  • "Every foreign key to a user is Restrict, so you can't delete someone with history. You block them instead."
04

Approval workflow

Every time entry moves through the same small state machine. Each arrow says who is allowed to take it.

How to explain it

  • "Two approval levels: the project's manager first, then its director."
  • "Rejecting and reopening both require a comment. The employee sees who rejected it, at which level and why."
  • "Reopen is the director's undo: an approved entry goes back to Rejected, and its hours leave the actuals immediately."
  • "All of this is one state machine in ApprovalService, and a test runs every status against every action, allowed and blocked."
05

Budget math: today vs. if everything waiting is approved

PRJ-0004 Atlas Network Monitoring from the demo data, drawn to scale.

How to explain it

  • "The budget is the client contract. Actual means approved hours only."
  • "Two numbers: what's left today (50 h), and what's left if everything waiting is approved (−5 h). The second is the early warning, before anyone approves the hours."
  • "Under 80 % used is on track, 80–100 % is near the limit, over 100 % is exceeded. The portfolio lists problems first."
  • "Once any hours are approved the budget is locked. A new deal means a new project."
06

Two people at once

Two approvals of the same entry arrive in the same moment, for example a double click or two open tabs.

How to explain it

  • "Optimistic concurrency: no locks while people read, and a conflict is detected at the moment of writing."
  • "Rules that compare against other rows, like the 12-hour daily cap, the one-entry-per-day rule and unique project names, run in serializable transactions instead."
  • "I have integration tests that fire real parallel requests at SQL Server. When I deliberately weakened the isolation level, the cap test caught 16 hours logged on one day, so the tests really do catch races."
07

Daily report: opening balance, period, closing balance

What the report returns when you ask for only part of a project, e.g. ?from=…&groupBy=week. Illustrative numbers on a 200-hour budget.

How to explain it

  • "It reads like a bank statement: opening balance, what happened in the period, closing balance."
  • "Without the opening balance, a 'last three weeks' view would start at zero and the remaining budget would be wrong."
  • "Group by day, week (starting Sunday) or month. Days nobody worked are left out, and the same data feeds the PDF export."
08

346 tests and what each group proves

Counted from the last full run, all passing.

How to explain it

  • "Most tests are fast unit tests of the business rules. The integration tests cover what mocks can't: SQL Server constraints, real query translation and real concurrency."
  • "The role-guard test reads every controller's attributes, so a new endpoint can't ship without the right [Authorize]."
  • "Even the demo data is tested. It has to obey every rule it demonstrates, otherwise the demo itself would be lying."
09

Employee use cases

Everything an employee can do in the system, as a UML use case diagram. Every use case needs a logged-in employee (a valid JWT with the Employee role).

How to explain it

  • "The employee's whole job in the system is logging hours and fixing them when they're rejected. Every use case maps to one endpoint in the Employee area."
  • "Submitting and editing share one set of rules: assigned to an active project, a date in the allowed window, one entry per project per day, and at most 12 hours a day."
  • "If an entry was rejected, editing it resubmits it. It goes back to the manager, and the employee can see the rejection reason in the entry's history."
  • "The employee only ever sees their own entries and their own projects. Anyone else's data is a 404."
10

Sequence: an employee submits hours

POST /api/Employee/TimeEntries followed through every layer, with what happens when all rules pass and when one fails.

How to explain it

  • "First the token: it must be valid, and the user must still be active with the same role. That's checked against the database on every request."
  • "The controller only reads the user id from the token and calls the service. All the rules are in the service."
  • "Cheap checks come first (hours, date in the business time zone). Then one serializable transaction checks the project, a duplicate day and the 12-hour total, and inserts."
  • "Two outcomes: everything passes, commit, 201 with the new entry; or a rule fails, rollback, and one clear 400 or 404 message."

14

Entity relationship diagram

Every table in the SQL Server database with its columns, types and keys. The tables come from the EF Core migrations; the AspNet* tables come from ASP.NET Identity.

How to explain it

  • "Six tables of my own plus the Identity tables. Every table of mine has a Guid key and CreatedAt / UpdatedAt, set in one place in SaveChanges."
  • "Users link to projects in three roles: director, manager and assigned employee. The employee also owns time entries, and a reviewer owns each review."
  • "The database enforces the rules too: unique codes and names, one entry per employee per project per day, and check constraints for hours and budget."
  • "RowVersion on time entries gives optimistic concurrency, so two reviewers can't approve the same entry at once."
